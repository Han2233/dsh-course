01 / 先建立坐标

从“会调用模型”到“能组装运行系统”

你已经了解 Agent 的基本循环：向模型提交上下文，接收回复或工具调用，执行工具，再把结果交给模型。本课研究的是这套循环运行之前，以及围绕它的工程问题：谁提供这些能力，谁把它们连起来，配置变化后谁负责维护它们？

能定位

知道入口、组装层、运行循环和能力实现分别在哪里。

能推演

看到 Profile、Bundle 和 Patch，能判断最终配置由谁决定。

能解释

说明 Preset 如何影响会话，以及配置更新为何不等于所有 Agent 立即换装。

dsh 的架构文档把系统描述为建立在 Cordis 上的插件组合：模型适配器、工具注册表、会话日志、运行循环都可以通过插件提供。插件向上下文贡献服务、事件监听与可撤销的注册。这里的“一切皆插件”是一条架构原则，不表示 Node.js、操作系统、Cordis 自身等基础设施也都能随意替换。

文档事实架构文档：Cordis 与核心包

本课的边界：重点是“能力从哪里来、怎样组装、怎样生效”。Cordis 内部的依赖反应与事件机制在第二课展开；模型请求和循环细节在第三课展开。本课出现这些概念时，先抓住它们在整个系统中的位置。

它面对的工程问题

先想象一个简单的 Agent 程序：main() 里创建模型客户端，注册工具，加载历史，再进入循环。这种方式很直接。但当你同时需要 Web 界面、无界面任务、SDK 接入、不同工具组合、可更新配置时，装配逻辑会逐渐变成多个入口中的条件分支。

dsh 把应用启动统一到具名 Profile，把组装内容放进可分发的 Bundle，把会话能力组合表达为 Preset。这让“使用哪一套能力”成为显式的配置选择。这是从源码组织推导出的工程收益；它不意味着所有项目都应该采用相同复杂度。

分析组装机制依据 Profile 模板、Web Bundle 清单、Preset 声明插件。

文档事实包分组职责图。这是阅读导航，部分包可能同时承担多个角色。

三条线为什么值得分开？

启动线回答“系统有哪些组件”；执行线回答“这次输入怎样被处理”；记录线回答“发生过什么、以后怎样恢复”。例如，服务器成功启动属于启动状态，工具调用属于执行过程，tool/result 属于被记录的会话事实。把三者混为一谈，就容易把“浏览器能打开”误判成“Agent 一定能完成任务”。

Session 在 dsh 中是追加式事件日志，模型历史由 deriveMessages() 等投影逻辑生成。它承载的并不只是一个可随手修改的聊天消息数组。这里先记住职责，第五课再研究历史重建与压缩。

03 / 基本概念

Profile、Bundle、Preset、Plugin 各管一层

这四个词都与“配置”有关，但它们回答的问题不同。理解它们，是读懂 dsh 其余部分的前提。

APPLICATION ASSEMBLY

Profile · 启动哪种应用

Harness home 下的一份具名组装。它的 package.json 通过 dsh.profile.bundles 声明有序 Bundle 列表，并拥有自己的补丁文件和外部插件依赖。

例如 web、headless。它不是一段系统提示词，也不等于某一个会话。

DISTRIBUTABLE COMPOSITION

Bundle · 分发一组组装内容

声明 dsh.bundle.patch 的 npm 包。该字段可指向一个补丁文件或有序文件列表；包还可携带实现代码与依赖。

例如 dsh-base、dsh-web-app。Bundle 不是“所有插件一次打包成无法覆盖的黑盒”。

AGENT CAPABILITIES

Preset · 会话选择哪组能力

由 dsh-agent-preset 插件声明 id 与 plugins。注册表预先加载其定义，并将 Agent 的作用域绑定到相应的已挂载版本。

例如 standard、minimal。它能改变工具、提示词片段和策略；不只是换一个模型名称。

RUNTIME CONTRIBUTION

Plugin · 实际贡献能力

Cordis 加载的行为单元。它可以提供服务、注册工具、监听事件或贡献提示词；也可以承担组合和装载职责。

工具通常由插件注册，但并非所有插件都是模型能调用的工具。一个 npm 包也可以导出多个插件入口。

源码事实Profile 数据结构与模板 · Bundle 清单 · Preset 注册表 · Cordis 概念

用一份实际组合来定位

在课程版本中，web 模板依次声明 @deepseek-ai/dsh-base 与 @deepseek-ai/dsh-web-app。前者插入核心运行能力，后者增加浏览器应用相关组件，并调整已有条目。Web 包的清单还按顺序列出 Standard、PTC、Minimal 与 Cordis（Creator）这些 Preset 的声明文件。

一个重要例外：sdk-minimal 模板只声明 dsh-sdk-minimal，不叠加 dsh-base。因此“所有 Profile 都是 Base + 一个界面”并不成立。另一个边界是：Headless 有自己的直接任务运行器，不能把 Web 的 Preset 路径机械套到每个入口。

核对五个随附模板 · Headless 的直接运行器组装

把“目录位置”与“加载标识”分开

packages/core/agent-loop/ 是源码位置，@deepseek-ai/dsh-agent-loop 是包名，某条 YAML 的 id: agent-loop 是树中的编辑地址；三者有关联，却不是同一类标识。一个包可以通过不同配置被多次挂载，因此 Patch 必须定位到条目，而不能只凭“这个包叫什么”猜测修改对象。

Preset 声明尤其容易混淆：外层 id: preset-standard 是 Loader 条目地址；里面的 config.id: standard 是供会话选择的 Preset 身份。改变其中一个，不等于另一个也被改变。

第一段：CLI 只做分派，应用参数交给插件

runCli() 先调用 parseDshArgs()，再根据模式进入 Profile 启动、插件管理、配置导出或 Schema 导出。dsh web 是启动 web Profile 的快捷形式。进入 Profile 分支后，CLI 调用 runProfile()，传入环境快照、Profile 名、Patch 路径与内部参数。

应用自己的参数通过 ctx.cmdlineArgs 交给注入这一服务的插件解释。以 Web 为例，启动参数可以影响 Web 启动服务，再由 Webserver 配置中的表达式读取。这使 CLI 不必亲自理解每个应用的全部选项。

runCli 分派 · runProfile 与 provideCmdline · Webserver 如何读取启动服务

第二段：先准备配置和包解析，再挂载插件树

prepareProfile() 装载 Profile，并写出内容为 [] 的根 cordis.yml。这个文件是 Include 的路径锚点，实际组合通过有序 Patch 形成。代码专门说明：根文件每次重写为空，是为了防止 Loader 写回的组合条目在下次启动时与 Bundle 插入产生重复。因此用户持久修改应放进 cordis.patch.yml。

composeProfile() 同时准备运行时包解析与本次覆盖文件。readProfilePatches() 决定层的顺序；底层 Include 的 applyEntryPatches() 负责把这些层应用到条目列表。“配置合成”首先是数据变换，“插件激活”才会进入组件的代码与生命周期。

prepareProfile / composeProfile · readProfilePatches · applyEntryPatches

第三段：Context、Loader、宿主准备与就绪信号

boot() 创建根 Context，安装 Loader，再执行宿主准备回调。这个回调提供 Profile 事实、环境快照、包解析和命令行服务；它在配置树条目挂载前执行。随后 Include 载入组合条目，Loader 等待树稳定，启动审计检查失败情况。

runProfile() 只有在启动与宿主准备成功、根 Fiber 仍活跃、Loader 仍存在且没有启动期停止信号时，才提交 appReady。这个顺序体现了一条重要区别：一个组件曾经成功启动，不代表整个应用已经完成启动。

boot 的实际顺序 · appReady.commit 的条件

静态复述路线：命令解析 → Profile 与包解析准备 → 有序 Patch → 根 Context / Loader → 宿主服务准备 → Include 挂载与审计 → 应用就绪 → 具体入口创建或接收 Agent 任务。是否启动即执行任务由入口决定：Headless 可直接处理命令中的任务；Web 就绪后仍需用户创建或使用会话。

Patch 的三条关键规则

  1. 插入与覆盖是两种操作。insert 可以向根列表或已存在的 Group 插入条目；新条目会加入索引，因此后面的 Patch 可以立刻定位它。
  2. 普通覆盖按条目 id 查找。指定了 name 时还会校验名称是否一致。找不到目标或名称不匹配时，会警告并跳过该 Patch，而不是自动创建一个替代条目。
  3. 覆盖是条目属性赋值。算法对每个覆盖字段执行 target[key] = value。因此提供一个新的 config，会替换整个旧 config；不递归保留其中没写的字段。

实验 02 · 观察最终配置怎样变化

虚构条目，真实覆盖规则

Base 插入一个虚构的 demo-executor：{ timeout: 30, retries: 2 }。下面的数值仅用于教学，不是 dsh 的默认参数。先只启用 Home 层，观察 retries 去了哪里。

此次应用的层

Base: { timeout: 30, retries: 2 }
Profile: { timeout: 60, retries: 2 }

组合完成后的条目

{
  "id": "demo-executor",
  "config": { "timeout": 60, "retries": 2 }
}
Profile 层最后生效：timeout 为 60，retries 为 2。

模拟只覆盖单条目的按 id 覆盖、整块 config 替换和目标不存在时的跳过；未实现 Group 插入、表达式求值、Schema 默认值与遥测特殊层。真实插件之后还会进行自己的配置校验，字段缺失不等于其最终运行时值必为 undefined。

这会怎样影响你的修改方式？

如果原 config 含有多个需要保留的字段，不能只写“想改的那个字段”就假定其余字段仍在。先查看最终组合和插件 Schema，再提交完整所需配置。另一方面，只覆盖条目级的 disabled 不会自动删掉 config，因为它们是不同属性。

举例：一处配置为什么看起来“改了没用”？

假设你在 Profile 层设置了 timeout: 60，Home 层又设置为 90。程序采用 90，与“是否保存文件”无关，而是后续层覆盖了它。若 CLI Patch 把目标写成 demo-excutor，它会被跳过；已有条目仍保留此前的值。排查应同时看层序、目标 id、警告和最终配置。

配置优先级 ≠ 插件启动优先级。层顺序决定最终有哪些条目及其配置；依赖注入决定插件何时具备启动条件。把某个提供方写在 YAML 更靠前的位置，不是处理依赖缺失的通用方案。第二课会把这一区别展开。
06 / 应用之内，如何组合会话能力

Preset 的变化，有明确的版本与生命周期

Web 组装会禁用部分原本处于宿主层的 Agent 能力条目，再通过各个 Preset 提供对应组合。比如 Standard 声明包含文件工具、Shell 工具、Skills、规划与压缩相关能力；Minimal 则包含精简的人设、持久 Shell 等自己的组合。Model 看到的工具与提示词因此可以随所选 Preset 不同而改变。

Web 中的宿主层与 Agent 层调整 · Standard 声明 · Minimal 声明

一份定义怎样变成可用能力？

Preset 声明插件的初始化调用 ctx.agentPresets.register(config)。注册表立即尝试激活该定义：创建作用域，挂载 Preset 子树，并记录一个带有 users 与 retired 状态的 Generation（已挂载版本）。Agent 选择它时，通过作用域父子关系加入这个版本。

相同 Preset 的同一版本可以被多个 Agent 共享。不能把这套机制画成“每创建一个会话，都完整复制一份独立 Preset 插件树”。与此同时，Agent 仍有自己的作用域；共享一个 Preset 版本不等于共享一份聊天历史，也不意味着提供方里的全部状态自动实现了会话隔离。隔离还依赖服务的实现和作用域规则。

为什么不立刻撤掉旧版本？

被替换的定义先将原版本标为 retired。collect() 只有在它已经退休并且 users === 0 时才清理作用域。这样，已绑定旧版本的 Agent 以及继承该版本的子作用域，可以继续使用它；新的 Agent 则绑定新定义对应的版本。

这里的收益是维持已绑定能力组合的连续性。代价是同一 Preset 的多个版本可能暂时并存，资源回收也需要引用与生命周期管理。这是根据实现和测试可以解释的取舍，不代表任意插件变更都能无中断热替换。

两种“变更”别混为一谈：更新一个 Preset 的定义，与让某个会话从 Standard 切换到 Minimal，是两件事。当前 select() 只允许在首个 Turn 开始前选择另一个 Preset，并记录 agent-preset/selected 事件；首次 Turn 开始后会拒绝切换。

select 的首轮边界检查 · 选择事件及其会话投影

一个坏 Preset，会让整个 Web 应用都坏掉吗？

不一定。注册表会保存定义的激活失败信息，使它在列表中显示为不可用；健康定义和宿主仍可启动。实际尝试绑定坏定义时才会被拒绝。另一方面，如果 Preset 子树把应隔离的服务泄漏到根 Realm，挂载审计会拒绝它；仅有缺失宿主依赖时，还需要等宿主树稳定后再复核，避免把尚在启动的提供方过早判断为缺失。

07 / 把组装与任务连起来

贯穿案例：修复文件，并运行检查

用户在 Web 中发出：“读取这个项目的配置文件，修正一个错误，再运行检查。”这是一条教学任务轨迹；模型具体会选择哪些工具、调用几次，并不是由本页预先决定的。

  1. 应用已就绪，但任务还没开始

    web Profile 的有序 Bundle 和 Patch 已形成插件树。模型适配、工具注册表、会话等能力已按当前组合提供；Web 应用能够接收请求。可用的模型凭据、网络或具体工作目录仍可能在真正调用时出错，启动成功不等于完成这些业务验证。

  2. 新建或使用会话，确定 Agent 的能力组合

    在 Web 的 Preset 路径中，Agent 的作用域与选定组合关联。这里假设使用 Standard。文件与 Shell 工具的可见性来自注册、作用域和策略共同作用，不能仅凭硬盘上安装了对应包，就判定模型一定能调用它。

  3. 用户输入唤醒执行，循环组织下一步

    默认 Agent Loop 从 Inbox 接纳输入，组装系统提示词与工具 Schema，并准备实际模型请求。Prompt、Tools 和 LLM 都通过相应能力接口参与；本课识别这些连接点，第三课解释 Turn / Step 的精确时序。

  4. 模型给出工具调用，Harness 负责执行

    若模型请求读取文件，工具注册表找到可见定义并经过执行流水线。若随后请求修改文件或运行检查，还要经过相应权限与环境策略；模型说“我要改”不会自动绕过这些策略。文件或进程提供方完成实际操作。

  5. 结果被记录，并成为下一次请求的依据

    工具结果作为会话事件记录。Loop 可以继续下一步，模型看到由日志派生的上下文，再决定下一步操作或给出回复。系统里的实时事件、持久日志与浏览器展示各有职责。

  6. 本轮结束，应用仍可以继续服务

    模型完成回答不等于 Web 进程退出，也不等于会话日志被删除。Headless 单次运行器的退出行为与 Web 不同。结束一轮任务、释放一个 Agent、关闭整个应用，是三个不同层次的生命周期。

08 / 边界与故障

失败发生在哪一层，决定你去哪里查

一个可组合系统必须处理部分失败。不能简单地认为“一个插件失败就全停”，也不能认为“网页打开就一切正常”。当前实现区分配置失败、启动关键条目失败、可选条目失败与 Preset 失败。

场景当前实现如何处理你的排查方向
Patch 找不到条目警告并跳过这条 Patch；不会自动新建目标。检查 id、Group 路径涉及的实际条目，以及它是否已被更早的层插入。
Bundle 无法解析或不兼容Profile 记录跳过的 Bundle 及原因；启动器报告这些情况。剩余组合是否可启动，还取决于其后依赖与审计。先看 Bundle 的诊断，再确认预期能力是否进入最终树。
根 Include 的配置无法加载Bootstrap Include 必须激活，失败属于启动失败。检查根配置及补丁格式、文件路径与报错来源。
已启用的关键条目未能激活启动审计拒绝启动；会汇总有关失败。代码对缺席或显式禁用的条目有特定规则，并非检查“所有关键 id 必须存在”。检查具体失败条目的导入、依赖与激活异常，不能只看最外层错误。
非关键条目激活失败如果没有关键失败，则记录警告并保留正常兄弟条目运行。核对所需功能是否恰好由这个失败条目提供。
一个 Preset 声明不可用列表保留失败诊断，绑定该定义时拒绝；健康定义可继续工作。查看 Preset 的子条目、缺失服务与 isolate Realm 检查。

Patch 警告分支 · skippedBundles / reportSkippedBundles · 启动审计边界 · Preset 审计

停止也属于启动器的责任

runProfile() 在启动阶段就安装信号处理与清理逻辑，而不是等所有插件启动完再处理停止。清理会尝试释放根 Fiber 与代理资源；启动出错时也会执行相应收尾。createProcessShutdown() 把重复的正常关闭合并为同一次 Promise，并提供有界的优雅关闭：当前默认等待上限为 5 秒，重复中断信号可升级为强制退出。

为什么启动还没完成就需要停止处理？因为同级条目可能仍在等待，其他组件却已创建资源或开始对外服务。没有明确的所有权与清理，就可能留下半启动的进程。这段解释是对源码注释与控制流程的归纳。

09 / 理解特色，也理解代价

可替换的能力，来自更明确的协作规则

dsh 把插件化应用到整套 Agent Harness，覆盖模型、工具、存储、循环与 UI 等部分。插件化、依赖注入、配置分层和事件机制本身都有既有技术背景；本课关注它们在 dsh 中如何组合，没有证据宣称它们由 dsh 首创。

教学对照：一个手工组装的程序

入口直接创建模型、存储、工具和 Loop。依赖关系在构造调用中可见，跟踪起来直接；新增多个入口或多种组合时，需要自己维护分支、共享初始化和清理。

// 教学伪代码
const llm = new ModelClient()
const tools = makeTools(localFs)
const loop = new Loop(llm, tools)
await loop.run(task)

dsh：声明组合，交给运行时管理

Profile 与 Bundle 表达应用组成，插件声明依赖，Preset 表达 Agent 能力组合。替换提供方与复用组装更有明确入口；读者也必须理解作用域、激活状态、层序与生命周期。

// 教学流程示意
Profile → 有序 Patch → 条目树
Loader → 插件提供服务与注册
Preset → 绑定 Agent 作用域
Agent API → 默认 Loop 执行

分析性比较左侧是本课自建的简化方案，不代表任何特定框架。右侧依据 dsh 架构 与本课已引用的实现。

特色设计可解释的收益需要付出的代价
连 Loop 都通过插件提供扩展方面向 Agent API，具体默认驱动器有替换位置。替代实现必须满足消费方依赖的行为约定；并非只换包名就能保证等价。
Bundle 可被后续 Patch 覆盖复用共享组合，并对部署或本次运行做明确调整。排查需追踪多个来源；config 整块替换容易丢失字段。
Preset 版本引用管理已有绑定与新定义可以并存，减少运行中能力突变。需要隔离、引用计数和回收机制；暂存多个版本也占用资源。
工具、提示词等注册有生命周期卸载和重载时可以撤销能力贡献。插件作者必须正确声明副作用与清理；框架无法替代码弥补所有资源泄漏。
会话事实与实时协调分开持久记录支持重建与恢复，实时事件支持运行中控制。新增模型可见信息时，需要设计对应记录，避免状态只存在于内存。

如果你只是做一个一次性的模型调用脚本，手工组装可能足够。需要多种入口、多个可维护的能力组合、插件扩展与持续运行时，dsh 的这种组织方式更值得研究。这里描述的是设计适配关系，不是性能或任务成功率的实验结论。

判断扩展位置：先问“我要改变谁的行为”

只改变 Web 应用的部署参数，先看 Profile Patch；给一个会话组合增加能力，先看 Preset；新增模型可调用操作，进入工具注册与能力接口；替换实际文件或进程执行环境，进入提供方；只有行为属于循环本身时，才研究 Loop。这个定位方法比“先找到最大的核心文件”更容易保持修改范围清晰。

架构文档：新行为的归属位置。接口 / 提供方 / 消费方的完整划分在第四课展开。

术语回看

Harness
模型周围负责运行、工具、环境、上下文与生命周期等能力的工程系统。
Context / 上下文
本课指 Cordis 的服务与事件上下文；与发送给语言模型的“上下文内容”不是同一个概念。
Profile / 应用组装
具名的启动组合，声明有序 Bundle 列表并拥有用户配置层。
Bundle / 组合包
可分发的配置层及相关实现、依赖。
Preset / 能力预设
供 Agent 选择的声明式插件组合，注册表管理其已挂载版本。
Patch / 补丁层
插入条目或按 id 覆盖已有条目的数据操作。
Scope / 作用域
用于限定与继承能力注册的上下文关系；不能仅凭“作用域”推断所有数据都已隔离。
Realm / 服务隔离域
使指定服务名解析到隔离实例的机制；Preset 服务泄漏检查会验证相关边界。
Generation / 已挂载版本
本课指 Preset 的某个运行时版本及其持有者，和 Session 日志格式版本不是一回事。
HMR / 热重载
监视变化并协调更新的机制；启用与监视范围来自配置，不等于任何修改都会安全地即时替换全部运行状态。
