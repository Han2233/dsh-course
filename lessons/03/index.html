01 / 从运行时到任务

插件已就绪，任务从哪里进入？

前两课让 Agent 的能力有了来源、依赖和清理规则。这一课跟随默认驱动器 ReactLoopAgent，把一条用户输入变成模型请求、流式响应和后续步骤。这里的 React 指这套推理与行动循环的实现命名，不是浏览器的 React 组件框架。

研究重点是“谁在什么时候推进状态”：用户发送的消息先进入 Inbox；驱动器在边界接纳输入；Prompt 组装器收集当前作用域中的贡献；LLM 运行时绑定路由与适配器；结果提交以后，再决定是否继续。你将能区分聊天界面、持久事件、模型可见消息和一次请求尝试。

本课所说“模型看到”，默认指 Loop 构建的请求视图。进入具体适配器后，文件、图片、工具更新与消息格式仍可能被投影或转换，不能把课程里的简化 JSON 当作 DeepSeek HTTP 请求体的逐字复刻。

02 / 三种粒度

Turn、Step、Attempt 分别回答不同的问题

一次 Turn 是驱动器打开并最终关闭的一轮任务边界。一轮里可以多次询问模型：模型先请求读文件，再请求修改、检查，最后回答。每次模型步骤以及它产生的工具执行构成一个 Step；请求失败后重试则可以仍在同一 Step 内，形成新的 Attempt。

turn() 先追加 turn/start，再调用 preStep。只有接纳决定为 enter 并且确实进入步骤，才追加 step/start。pre-step 被 reject 时，可以有一轮 blocked 的 Turn，却没有模型请求；首轮接纳消息为空时，也可以直接完成而不消耗模型调用。

Step 内部的 while 循环管理重试；Turn 内部的 while 管理后续步骤。前者复用这一 Step 的已渲染组装结果，不重复 pre-step，也不重复追加已接纳用户消息；后者会重新进入边界，读取新的引导和组装贡献。把所有循环都称为“再试一次”，会掩盖重复消息或工具误重放的问题。

计数什么时候增加不应被误解成
Turn开始新轮任务每来一段流式文字就增加
Step接纳并进入新的模型步骤一次网络重试
Attempt一次新的流式模型尝试整个 Agent 生命周期或全部会话
Tool call响应中要求调用一个工具一个 Step 只能有一个工具调用

03 / 输入队列

发送消息，和消息进入模型，是两件事

Inbox 有 next-turn 与 next-step 两个待处理列表，变更通过 agent/inbox/spliced 记录。投影重建会检查坐标和重复消息身份。这让“还在排队的输入”本身有可恢复的事实，而不只是一个临时数组。

入口目标队列是否唤醒典型用途
followupnext-turn是把新任务排到后续轮次
steernext-step是在下一步骤边界接纳中途引导
injectnext-step否放入上下文，等待驱动器已有工作或后续唤醒

claim() 先移除 next-step 的全部待处理消息；若目标为 next-turn，再追加取出一条 next-turn。随后还要经过 pre-step 决策，才真正接纳到模型历史。消息离开待处理队列，不等于已经发给模型。

忙碌时 steer 不会改写已经冻结并开始传输的请求，只能等后续边界。idle 时 steer 可以唤醒驱动器，所以它也可能开启一轮；inject 本身不会唤醒。已经 abort 的活动收到新的唤醒输入时，会把它安排到 next-turn，避免把新任务塞进正在退出的轮次。

取消默认清空两个队列；keepInbox 保留尚未 claim 的消息，但不把已经取走的批次自动塞回去。取消后保留下来的队列可能停放等待新的唤醒。工作台会把两个列表直接显示出来，让这些差别可观察。

04 / Prompt 与工具

组装结果来自作用域，而不是拼接全部日志

在 preStep 中，驱动器先 claim 输入，再调用 systemPrompt.assemble，渲染运行时上下文，并把提议交给 agent/pre-step waterfall。第二课中的可逆贡献在这里开始影响模型请求：可见的变量、提示片段、上下文片段和工具 schema 都从当前作用域链汇集。

变量沿全局到近端作用域解析，较近同名变量优先；提示片段先按作用域遮蔽同名项，再按规则排序。工具提供者输出 schema，参数会被复制。组装后的对象经过 system-prompt/assemble waterfall，监听者可以改写它。最终结果不应被想象为“所有插件各加一句话”这样简单。

complete 提示片段是一个重要例外：有效 complete 片段会在组装 waterfall 后作为唯一的系统片段恢复；同时有多个 complete 会报错。不要据此推断工具和上下文全部被清空，它约束的是提示片段维度。渲染时空片段被过滤，其他片段以空行连接。

模型需要工具名称、描述和参数结构，通常不需要插件源码。工具返回的文件内容属于后续消息历史，能力目录属于 tools。只有名称一致也不够判断 schema 未变；工具 schema 的变化和名称增删是两个观察维度。

05 / 请求快照与适配器

先绑定路由，再决定这一次请求的边界

prepareRequest 从 Agent 配置与已记录请求头提出 provider、model、reasoningEffort、maxTokens 等值，经 agent/request waterfall 调整。没有有效 provider/model 会报错。随后 llm.prepareCall 解析准确模型元数据、默认值和能力，并把一次调用绑定到当前 adapter 注册。

这解决一个实际一致性问题：如果先读取适配器 A 的能力，再在异步等待后从已替换的注册表拿适配器 B 发请求，日志记录和实际行为可能不一致。PreparedLlmCall 固定本次注册与解析结果，只允许分发一次，并检查请求配置没有被偷换。它不是可以任意复用的连接池句柄。

buildRequest 记录或更新 request/header，并按需记录 request/context。header 不需要每次调用都重复追加：首次、变更或请求序列变化有不同 reason。随后从会话 surface 派生消息，冻结消息对象、列表和请求，避免请求在传输中被插件原地修改。

源码的 Loop 请求没有单独的 system 字段，系统指令通过 system/message 的投影进入消息。某些路由允许在历史中追加系统提示更新；另一些需要归并到头部。判断依据来自本次 prepareCall 的能力，不是凭模型名称猜测。序列边界、工具变化或 surface 替换都会影响协调；本课只建立这层边界，第五课深入历史投影。

进入 adapterStream 前，运行时还会按路由能力投影文件、图片和工具更新。最外层 llm/stream 是 waterfall，第二课的环绕扩展可以在这里观察或包裹流。该调用链里的不同错误有不同归属，不能把任何异常都当作网络故障重试。

06 / 流式结果

用户看见了文字，不代表它已成为完整消息

一次模型尝试会产生进程内的 start、chunk、end 通知。AssistantStreamAttempt 把 chunk 同时交给压缩累积器与块组装器；界面可以据此显示增量文字。结束时，驱动器才根据 finish 决定记录 assistant/message，还是仅记录 assistant/attempt。

工具调用的参数可以分块到达。半截 JSON 不具备完整调用的语义，不能一边收到 {"pa 就去执行读取。正常完成时，从组装好的 assistant 内容块中提取 tool-call；取消时，interruptedBlocks 保留安全的已交付前缀，测试特别覆盖了丢弃半截工具调用、保留其前面的完整文字。

本快照中的 push 负责累积并发布瞬时 chunk；settle 先追加匹配的持久消息或尝试记录，再发布 end。append 失败时则发出 abandoned 终态。不要把每个 UI chunk 都解释为一条持久 session 事件。这里按实际实现讲解，而不是仅凭“持久流”这个描述推断提交时机。

响应的 finish 也有意义：max-tokens 表示输出达到上限，不等同于任务自然完成；错误和 aborted 会进入恢复或结束路径。真实流还可能包含 usage、reasoning 和 replay 状态，工作台只展示可见文本与完整工具调用，不生成或伪造模型内部思考。

07 / 继续与停止

工具结果回到历史，下一步才重新请求模型

成功响应先记录 assistant/message，再检查 finish 和内容块。达到 max-tokens 时结束该步骤；没有工具调用时返回 completed；有工具调用时进入 executeToolCalls。工具结果如果声明 concludesTurn，可以结束轮次，否则返回继续信号，让 Turn 循环进入新步骤。

“没有工具就立刻退出”仍然过于粗糙。Turn 在候选结束且没有 next-step 时会调用 agent/turn-stopping；监听者可能在边界加入新的工作。已有 next-step 也可以让这一轮继续。max-tokens 还是 sticky 的：后续步骤普通完成，不能把本轮已经达到上限的事实降级为 completed。

一个响应可以要求多个工具。默认调度器把 exclusive 调用作为屏障，把 parallel-safe 调用放进有界滚动池；不是无条件 Promise.all，也不是所有工具永远串行。当前默认并行上限来自常量 10，但真实配置可以覆盖。策略、持久结果和结果上下文还要维持模型顺序，第四课详细分析。

关键的数据闭环是：assistant 工具请求与 tool 结果成为可投影历史，下一次 buildRequest 才让模型看到观察结果。Agent 的“继续思考”并不要求模型一直持有服务器进程的内部内存；驱动器负责把有关事实重新组织成请求。

08 / 重试、错误与取消

请求重试不会自动重放不明结果的工具

LLM 运行时把适配器选择、分发和迭代阶段的故障归一化为终止 finish。Loop 记录失败 attempt，再发出 agent/request-error waterfall。处理器返回 { kind: 'retry' } 才继续当前 Step 的尝试；没有接管则以结构化 LlmError 结束。

Middleware、自定义恢复监听、结果处理或工具扩展抛错，仍可以直接结束轮次。它们不一定进入请求重试钩子。把本地插件错误误判成服务暂时不可用，只会重复触发同一错误，甚至重复外部副作用。

故障 / 控制本快照的主要处理教学工作台的简化
适配器暂时故障失败 attempt → request-error → 策略决定首次失败、只允许一次手动推进重试
重试等待先持久记录 retry，再可取消退避，之后 retry-started不真的等待秒数；按钮代表等待结束
普通策略检查代码、最大重试次数和延迟；可用提供方 Retry-After不模拟完整策略参数和抖动
插件或工具异常步骤恢复必要的结果配对，再结束轮次展示能力失去后的预设错误结果
用户取消AbortSignal 传播；默认清空 Inbox；结算前缀和边界可在每个教学里程碑取消
工具结果不明使用保守错误结果补齐历史不自动重新执行未知结果操作

llm-retry 的策略属于 provider 配置。它支持 normal 与 always 等模式；always 不等于取消也会被忽略。退避信号会融合轮次取消与插件生命周期取消，等待可以被打断。普通策略会检查最大重试次数；无界恢复模式仍有自己的终止边界和下游委托规则，课程不建议仅凭名字当成“什么都无限重试”。

取消是另一条路径：若已有安全文本前缀，记录 interrupted 的 assistant/message，让用户看到的内容在后续请求中有依据；没有可见内容时，可能仅保留 attempt。未派发但已在完整 assistant 响应中声明的工具调用，需要合成 call/result 配对，避免悬空历史。

步骤失败时，已记录 tool/call 但缺少已提交结果的调用可能获得 TOOL_OUTCOME_UNKNOWN；尚未开始的获得 TOOL_NOT_STARTED。它们说明的是证据不足，不是证明操作绝未发生。不能把这种恢复结果当作自动重试文件写入的授权。

动手搭建 / 03

让任务草稿进入可观察的模型循环

先跟随带“建议下一步”标签的高亮按钮完成宿主组装，再安装教学插件、接通 fs、完成初始化。本课把教学贡献扩展为 demo.read、demo.edit、demo.check 三个占位声明。发送任务后逐步推进，或自动播放；也可以不安装插件，对照“没有工具声明”的纯文字路径。

模拟边界：模型响应和工具结果由预设脚本产生；自由文本只用于观察队列与请求，不会被真实模型理解。文本分段不是 token 计量。默认脚本分四步展示读、改、查、总结；本课不读写文件、不执行 Shell。请求 JSON 采用简化内容结构，省略 toolHistory、实际协议投影和异步清理细节；不模拟 pre-step 拒绝、turn-stopping 或 max-tokens 后的继续步骤。停止宿主会直接完成教学取消，真实取消仍需等待异步工作收敛。

      09 / 完整任务轨迹
      读、改、查，为什么要连续请求四次？
      输入“读取配置，修正错误，再运行检查”，不是把这个字符串直接循环发送四次。每个请求携带的事实不同：初次有任务与能力目录；读之后多了读取观察；改之后多了修改结果；查之后才有检查结论。下面是教学脚本，不代表真实模型一定选择这个顺序或工具数量。
      Step请求新增的事实预设响应之后进入历史的结果
      1已接纳用户任务、三个教学 schema请求 demo.readtimeout 为 0 的预设读取结果
      2前一步 assistant 调用与读取结果请求 demo.edit预设修改成功
      3修改调用与结果请求 demo.check预设检查通过
      4全部调用结果给出最终文字总结完成的 assistant 消息
      如果第一步第一个 Attempt 返回服务不可用，失败尝试会留下记录；它不应凭空增加第二份用户消息。第二个 Attempt 仍属于 Step 1，复用已渲染 Prompt 和已接纳输入，只重新准备模型调用。工作台可以切换这两个请求快照进行对照。
      如果中途卸载教学插件，已经构建的请求快照不会被篡改；后续步骤重新组装时可看到工具声明变化。若一个已返回的工具调用在派发前失去能力，执行层必须处理失败，而不是因为 schema 曾出现就假定调用永远可用。本工作台返回明确的教学错误并停止后续修改；真实工具流水线细节属于第四课。

      一致性来自明确边界，也带来更多状态
      把用户输入直接 append 到一个 messages 数组，再反复调用模型，是合理的最小原型。dsh 的默认驱动器还要处理排队、抢占引导、持久恢复、作用域变化、重试和取消，因此引入更多显式状态。以下对照是课程自建的简化方案，不代表任何特定外部框架。
      同一个问题简单循环dsh 本课实现
      新输入到达直接改共享消息数组Inbox 与步骤接纳边界
      重试容易重复追加用户输入Step 内复用接纳结果，Attempt 独立记录
      请求中的能力变化共享对象可能边发送边改组装与冻结快照，下一边界再更新
      取消流停止显示即可，但历史可能丢前缀结算安全前缀、attempt 与 turn 边界
      服务与适配器替换配置解析和实际分发可能错配PreparedLlmCall 固定一次调用
      代价少量状态，容易启动需要维护日志、投影、边界与错误分类
      特色在于这些机制怎样接上 Agent 插件体系，不是发明了流式生成、重试或工具循环。它们的组合让“用户看到什么、日志提交什么、下一次模型收到什么”更容易核对；同时也要求扩展作者尊重 waterfall 协议、冻结请求和取消信号。
      症状优先核对
      发了消息但没请求是 inject 还是唤醒输入？是否停放队列？是否被 pre-step 拒绝？
      新指令没影响当前回复是否已经越过请求冻结边界？应检查下一 Step
      请求次数增加但 Step 不变可能是 request-error 返回 retry，而不是新任务
      显示过文字，历史里却没成功回答可能是失败 attempt；区别正常完成与取消前缀
      停止后又执行了操作检查取消传播、已派发调用与未开始调用，不能只看 UI 按钮
      没有 tool-call 还没结束检查 next-step、turn-stopping 和轮次边界
      使用哪种复杂度应由任务需求决定。短小的一次性脚本不必机械复制整套日志协议；长期运行、可恢复、可扩展的 Agent 更需要这类边界。页面中的模拟帮助定位概念，不能替代对真实网络、工具和并发路径的运行验证。

      12 / 回顾与下一课
      三个问题，定位一次模型交互
      回看任何一次请求时，先定位：它属于哪一轮、哪一步、哪次尝试；它使用哪一个冻结的消息与工具快照；它怎样结算为消息、失败尝试或取消前缀。这三个角度连接了本课的队列、请求和流式结果。
      Inbox
      尚未接纳的 next-turn / next-step 输入队列。
      Turn
      一轮任务的开始与结束边界。
      Step
      一个模型步骤及其工具处理；可以包含多次尝试。
      Attempt
      一次模型流式尝试，成功、失败和取消各有结算。
      PreparedLlmCall
      绑定本次适配器、解析配置与能力的单次分发句柄。
      Surface / 派生消息
      会话中对模型可见的内容视图；不是原始事件全集。
