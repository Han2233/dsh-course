01 / 承接第一课

把插件树变成有生命的系统

第一课把 Profile、Bundle 和 Preset 组装到一棵树里。本课沿着树进入内核：一个插件为什么还没启动，它读到的服务属于谁，服务消失后如何撤掉贡献，以及替换实现为什么需要先完成清理。

你已经理解 Agent 的基本结构，因此这里把注意力放在 dsh 使用的 vendored Cordis 实现。本课中的 Context 是依赖与事件上下文；它与模型接收的消息上下文是两件事。下一课才进入模型请求。

本课的三个阅读目标：能沿一个服务的出现与消失追踪消费者生命周期；能区分作用域可见性和资源所有权；能解释一次卸载实际撤销了什么。先看机制，再在 Agent 工作台中操作，最后回到源码摘录。

02 / 运行时对象

同一份插件代码，可以有多个运行实例

一个简单的 Agent 原型可以把工具、模型对象和回调都放进全局变量。能力少、进程不更新时，这种做法容易理解。随着会话组合、插件重载和服务替换加入，问题会变成：谁创建了这个回调，哪个 Agent 能看到它，提供方消失时谁来撤销它？这是对工程问题的分析，不是作者首创性的声明。

Cordis 把代码身份、实例生命周期和访问视图分开管理。RegistryService.plugin() 先把函数、类或带 apply 的对象归一化成 callback；相同 callback 复用 Runtime 记录，但每次加载都新建 Fiber。重复加载一个插件，不等于复用同一份实例状态。

对象解决什么问题容易混淆的边界
Plugin / 插件入口要执行哪份实现不要求所有插件都继承 Service；函数和 apply 对象也可以
Runtime / 代码记录按 callback 归组所有 Fiber不是单个插件实例，也不是某个 Agent
Fiber / 挂载实例跟踪依赖、配置、状态与清理此处不是 OS 线程或模型执行 Step
Context / 访问视图解析服务、创建子上下文、分发事件extend 本身不会创建独立 Fiber
Service / 服务为消费者提供命名接口一个插件可以只注册贡献，不提供新服务

Context 构造函数建立根 Fiber 和 reflect、registry、events、logger，再返回 Proxy。ctx.tools 这类属性访问会经过解析逻辑；不能把 Context 当作普通字典复制，然后期待生命周期语义仍然成立。

03 / 服务与依赖

inject 声明的是持续依赖，不只是启动参数

以真实 tool-fs 为例，它声明 inject = ['tools', 'fs', 'systemPrompt']。tools 提供注册入口，fs 提供文件接口，systemPrompt 支持相关提示贡献。插件实现调用这些接口，不需要知道底层文件系统具体由哪个包提供。

注册服务时，provide() 将实现写入按隔离 label 索引的 store，并把撤销函数登记为当前 Fiber 的 effect。同一个 label 已有服务实现时，再次 provide 会报错；它不是“后来者无条件覆盖”。Service 子类的构造函数也通过这条路径注册自身。

Fiber 的 _checkImpl() 要求提供方处于 ACTIVE，并执行可选的可用性检查；_refresh() 把依赖提供者的 uid 组成 epoch。缺少任意服务时 epoch 为 INACTIVE。这个 epoch 是当前依赖组合的身份标记，不是模型版本，也不意味着会跟踪服务对象每个字段的变化。

服务进入或离开 ACTIVE，或提供项被撤销，会通知同一隔离域中的依赖者，重新检查并刷新 epoch。依赖变了，旧激活轮次先卸载，再决定等待还是重载。因而把消费者放到 YAML 最后，只解决偶然的初始化先后，无法替代持续的依赖声明。

访问方式行为使用边界
inject + ctx.fs插件在满足依赖后运行，受服务变化驱动常规必需能力依赖
ctx.get("fs")显式查询；默认只返回 ACTIVE 提供方的值不会因此自动声明依赖或建立重启关系
ctx.fs（未声明）插件代理会沿允许的父 Fiber 依赖链查找，否则报错不是任何插件都能随意读全局服务
ctx.fs = value由已有服务的拥有 Fiber 更新值普通 set 不会直接执行 notify；不等于替换提供方生命周期

一个服务对象构造出来，还不等于它对依赖注入可用。初始化期间提供方可能仍是 LOADING；严格查询和依赖检查会观察其生命周期状态。等待中的 Fiber 也可能被 await() 返回，所以“await ctx.plugin(...) 完成”不能孤立地当作 ACTIVE 的证明。

04 / 状态与失败

PENDING 可以恢复，DISPOSED 结束这个实例

把插件状态理解成“开 / 关”会丢掉最有用的信息。PENDING 说明条件还没满足；LOADING 说明插件代码正在初始化；ACTIVE 说明本轮激活完成；UNLOADING 表示正在清理；FAILED 保存初始化或配置错误；DISPOSED 表示这个非根实例已被明确移除。

_reload() 会先经过一个微任务检查点，确认 epoch 没有过期，然后解析配置、执行插件入口。执行抛错会记录错误、使 epoch 失活并进入卸载；fiber.await() 等待当前 inertia 完成，再重新抛出保存的启动错误。错误不是仅仅画成红色图标，它会影响启动审计和调用方控制流。

restart() 保留实例身份，先设为失活再刷新；dispose() 清空非根 Fiber 的 uid，移除拥有关系并等待清理。不要把它们与 HMR 替换代码混为一谈。根 Fiber 的 dispose 实现走 restart 路径，本课状态图主要针对普通插件 Fiber，不把根对象画成永远不可用的普通插件。

配置更新也有入口：ACTIVE 时先解析新配置，再走 internal/update waterfall；监听者可以接管或不调用 next。默认路径 restart。未激活时则推迟配置解析，等依赖可用后再处理。工作台的“重启”只模拟默认生命周期路径，没有实现完整配置表达式求值。

05 / 副作用与所有权

清理的对象，是插件留下的可见贡献

读文件是业务操作；把一个 read 工具登记进工具目录，是运行时注册副作用。插件消失时要撤销的是后者，以及它建立的监听、计时器、子插件等资源。一次业务写入已经改变的文件不会因为卸载插件而自动恢复。

ctx.effect(execute, label) 立即执行 setup，把返回或 yield 的 disposer 收集起来，并在拥有者卸载时撤销。ctx.on() 内部也使用 effect 注册监听；工具注册表的 register() 则把作用域、注册层与 effect 关联起来。要先理解拥有关系，才能判断一项注册会随谁消失。

一段最小的所有权示意

以下是教学伪代码，名称与 registerDemo 接口是虚构的。它只演示资源先登记、再成对撤销；真实工具注册需要 schema、输出渲染等声明，第四课再展开。

ctx.effect(function* () {
  yield registerDemo('demo.read') // 返回撤销函数
  yield subscribeDemo('demo/inspect')
}, 'demo-contributions')
// 同一 effect 内清理：先取消监听，再移除 demo.read。

逆序清理的边界

同一个 effect 收集的 disposer 逆序执行，遇到 Promise 会衔接等待。可是 Fiber 的 _unload() 对它拥有的多个 effect 使用 Promise.all：不同 effect 的完成时间没有全局串行保证。需要先停止监听再关闭连接时，把顺序写进同一组合 effect 或一个明确 await 的清理函数，不要靠“先注册后清理”的想象。

当前实现还会在运行 setup 前把 effect 放进拥有者的列表，避免 setup 内重入触发卸载时漏掉它；异步 setup 未完成时，清理会等待 setup 结果。同步 setup 抛错则回滚已收集的清理。测试覆盖了这些重入和部分初始化场景，但课程没有运行 dsh 测试套件。

自动清理的范围限于已登记的资源。裸全局数组、未托管的 setInterval 或无法撤销的外部请求，不会因为放在插件函数里就自动变得可逆。公开 disposer 是 single-shot；重复调用不应重复删除资源。卸载期间再注册 effect 会被拒绝。

06 / 作用域与隔离

“看得见”和“归谁清理”要一起追踪

这里有三种相关但不同的机制。Context.extend 用原型继承扩展视图；Context.isolate 为某个服务名换一个解析 label；dsh-scope 则为贡献注册与事件路由添加作用域键。它们没有共同的“全部数据隔离”开关。

机制改变什么保留什么
ctx.extend(meta)覆盖子视图的元数据本身不创建 Fiber，也不自动复制服务
ctx.isolate("fs")fs 对应的服务解析 label其他未隔离服务仍沿原有关系解析
createScope(ctx, key)创建有拥有关系的作用域，给贡献与事件带标签只有感知 scope 的 API 才按标签分层
ctx.intercept(name, config)增加服务专用的上下文配置不是第一课的 Patch；服务可自定义 merge

服务隔离可类比给同名电话分配不同分机：Root 的 fs 和隔离域里的 fs 可以同名而指向不同实现。这个类比只说明查找规则，不提供操作系统安全边界。用同一 label 创建两个隔离上下文，还会让它们加入同一服务域。

注册贡献沿父链向下可见，较近的同名定义优先；作用域事件则允许祖先监听后代的活动。比如 A 的状态事件可以被 Preset 层监听，B 自己的监听不会因此收到 A 的事件。scopeTarget() 通过 Context.filter 路由，未打标签的监听保持全局，显式 global 选项还能绕过筛选。

这些规则解释了第一课为什么要让 Agent 绑定 Preset 的 Generation：作用域父链能复用组合贡献，同时保留 Agent 自己的注册。它也解释了边界：把带 scope 的 Context 交给一个不感知 scope 的普通服务，并不会改变该服务内部的全局数据结构。

07 / 事件语义

waterfall 是环绕调用，serial 也可能提前结束

服务方法适合直接请求某项能力；事件适合让多个插件参与观察或策略。本课不背所有事件名，而是读懂分发契约。TypeScript 类型合并能描述事件参数，具体执行次序仍由所调用的分发方法决定。

模式等待与次序停止 / 返回规则
emit按监听顺序同步调用，不等待返回的 Promise忽略返回值；同步抛错可中断后续调用
parallel并发调用并等待 allSettled收集错误后抛 AggregateError；不是收到首个错误就停止其他监听
serial逐个 await遇到首个 bail 值返回，不保证所有监听都执行
bail同步逐个调用遇到首个 bail 值返回
waterfall监听层调用 next，包裹下游不调用 next 可短路；返回外层结果，框架本身不是 async 函数

isBailed() 只把 null、false、undefined 当作“继续”。0 和空字符串也会停止 bail / serial。把它写成 if (result) 会改变协议。另一个源码细节是 parallel 当前内部把 dispatch 的模式参数写成 emit；它的等待行为仍由 allSettled 决定，诊断事件里的模式字符串不能单独当作执行策略的证据。

正常路径是 A 进入、B 进入、核心、B 返回、A 返回。B 短路时核心和 B 的下游不会运行，但 A 仍收到 B 的返回值。如果监听者只想加一条标记却忘记 next，就可能无意吞掉默认操作。这也是 internal/update 能接管默认 restart 的原因。

“waterfall 不 await”并不代表禁止 Promise：监听者可以返回 Promise，调用方按自己的事件契约等待。关键在于框架如何把 continuation 传给下一层；它不是常见的“上一个监听的结果自动成为下一个参数”的流水线。

08 / 更新边界

插件重启与源码热替换，是两层工作

restart 使用当前 callback 和配置重新激活一个 Fiber；修改 JavaScript 文件还需要监听变化、确定受影响模块、更新缓存、找到对应插件并重新挂载。后者由 dsh-hmr 协调。仅有可逆 effect，并不意味着任何文件变化都会立即被发现。

runExclusive() 把操作接到同一 Promise 链，并拒绝嵌套事务；队列保存的 catch 使一次失败不会永久阻塞后续任务。源码替换先准备新模块，之后卸载旧实现并激活替代实例；失败路径恢复缓存并尝试重新注册旧插件。外部文件写入、远程请求等副作用不因此获得数据库式事务回滚。

默认 Profile 路径中 Base 可启用配置监听，但源码模块监听范围由 root 配置决定；root: [] 只保留显式配置监听。Headless、SDK、ACP 的默认配置另有禁用安排。HMR 关闭或没有覆盖目标目录时，修改不会自动生效。安装包版本替换、Node loader 内部接口和浏览器模块图也有额外限制；本课不把简化的重启按钮描述为完整 HMR。

      09 / 完整案例

      从缺失 fs 到能力恢复，沿拥有关系走一遍

      设教学会话已经绑定 Preset，tools 和 systemPrompt 已可用。我们加入文件能力插件，但 fs 提供方尚未上线。此时模型请求数仍为零，问题发生在运行时组装阶段。

      变化内部原因对会话的可见结果
      安装消费者建立 Fiber 并解析 inject；fs 缺席使 epoch 失活PENDING，尚无 demo.read
      接通 fs同域消费者被 notify；依赖完整后开始加载LOADING，能力尚未承诺可用
      初始化完成登记工具和监听，并进入 ACTIVE能力目录出现教学工具
      撤掉 fs依赖快照失效，当前轮次卸载UNLOADING；等待贡献撤销
      清理完成原贡献移除，实例仍存在PENDING；事件监听数归零
      恢复 fs同一实例可进入新一轮加载完成后重新获得一份能力，不重复登记

      这条轨迹解释了“界面还在，但某个工具消失”为什么可能是正确行为：宿主不依赖这个局部能力继续显示页面，而消费者在提供方缺席时撤销自己的贡献。真实系统还会有更多依赖者、作用域、缓存及在途任务；本课没有模拟正在执行的工具怎样取消，那要结合第四课的执行协议。

      把案例映射回真实 tool-fs：必需依赖之外，它还通过 ctx.inject(['attachments'], ...) 条件性注册 read_image。缺少 attachments 可以让这个嵌套能力等待，而不是要求所有文件能力都以它为前提。这展示了“整插件必需依赖”和“局部可选能力的子插件”两种粒度。

      失去依赖调用方逐处检查引用是否有效依赖者卸载、清理，再等待或重载
      清理手工维护每个回调的 removeeffect 把 disposer 归属到 Fiber
      按会话贡献自己维护会话 id 到注册项的映射dsh-scope 提供可见性与拥有关系
      成本早期代码直接，规模大后容易遗漏要理解 Proxy、依赖、状态和异步清理

      这些收益来自已有插件、依赖注入和资源管理思路的组合，课程不把它们称作 dsh 独创算法。dsh 的特点在于将 Agent 的工具、提示、会话与应用组合放进同一套运行时约定，同时为 scope、Preset 版本和 HMR 加入相应机制。

      现象先检查不要直接得出的结论
      插件始终 PENDING必需服务的 ACTIVE 状态、隔离 label、可用性检查不是多等几秒或调 YAML 位置就一定能解决
      服务已存在但属性读取报错本插件或允许的父依赖链是否有 inject不能因为根能 get 到就断定所有子插件都可读
      每次重载多收到一次事件监听是否通过 ctx.on 或正确 effect 托管不一定是模型重复调用
      清理偶发先后颠倒是否把有顺序要求的工作分散到不同 effect不能假定全局逆序
      重启后工具仍不可见注册所在 scope、服务缺席和初始化错误不要只看包已安装
      改源码没有效果HMR 是否启用、root 范围、实际载入模块restart 不会自行导入新代码

      不建议为了使用框架而拆出大量没有独立生命周期的小插件。只有当一项能力有独立依赖、作用域、配置或清理需求时，这种拆分才更容易解释。对一次性脚本，直接构造对象和显式 finally 清理可能更简单；对长期运行的可组合 Agent，统一所有权的收益更明显。这是基于本课实现的工程判断。

      12 / 图解回顾

      用三条坐标定位一个运行时问题

      Fiber
      插件的一次挂载实例，拥有依赖、状态与副作用。
      Epoch
      此实现中描述依赖组合的激活身份；变化会驱动生命周期转换。
      Inertia
      当前正在进行的加载 / 卸载 Promise。
      Disposer
      撤销一次注册或释放资源的函数。
      Realm / label
      同一服务名在不同隔离域中的解析身份。
      Scope key
      dsh 贡献继承与事件路由使用的不透明身份，和服务隔离 label 不同。
      Waterfall
      通过 next 环绕下游的分发机制。
